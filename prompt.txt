============================================================
2. PROJECT PRINCIPLE
============================================================
The central design principle is:
    DO NOT BUILD EVERYTHING FROM SCRATCH.
Instead:
    SELECT THE BEST BASE
            ↓
    UNDERSTAND IT COMPLETELY
            ↓
    IDENTIFY WHAT IT ALREADY SOLVES
            ↓
    IDENTIFY WHAT IT DOES NOT SOLVE
            ↓
    FIND THE BEST RESOURCE FOR EACH GAP
            ↓
    INTEGRATE ONLY THE MISSING CAPABILITY
            ↓
    TEST AGAINST THE BASELINE
            ↓
    KEEP / MODIFY / REJECT
            ↓
    MOVE TO THE NEXT GAP
Every new capability must justify its existence.
For every proposed addition answer:
1. What problem does it solve?
2. Does the current baseline already solve it?
3. Is the existing solution complete?
4. If incomplete, what exactly is missing?
5. Is there an existing high-quality implementation?
6. Should we integrate, adapt, wrap, or build from scratch?
7. What dependencies does it introduce?
8. What performance cost does it introduce?
9. What security risk does it introduce?
10. How will it be tested?
11. How will false positives be measured?
12. How will the new capability interact with existing findings?
Never add functionality simply because it appears useful.

20. DEDUPLICATION
============================================================
Expect multiple skills to discover related symptoms.
Example:
    Entity skill:
    Missing structured entity data
    Content skill:
    Poor semantic identity
    Baseline:
    Weak entity representation
These should potentially become one coherent finding with multiple evidence sources rather than three noisy findings.
Implement a deduplication/aggregation strategy.
Do not over-merge unrelated findings.
============================================================
21. EVIDENCE
============================================================
Every non-trivial finding should have evidence.
Evidence should be:
- concrete
- traceable
- understandable
- tied to the audited resource
- sufficient to justify the finding
Avoid statements such as:
    "The site is bad for AI."
Prefer:
    "robots.txt disallows the relevant AI retrieval crawler path."
The final system should explain:
    WHAT is wrong
    WHERE it was observed
    WHY it matters
    HOW it affects AI readiness
    WHAT should be changed
============================================================
22. FALSE POSITIVE CONTROL
============================================================
False positives are a major quality risk.
Every detector should be evaluated against:
    true positive
    true negative
    false positive
    false negative
Do not maximize the number of findings.
A smaller number of accurate findings is preferable to a noisy report.
