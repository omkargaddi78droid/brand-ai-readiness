# Deep Research Prompt — Cycle 23: New Capabilities, Blocked-Item Rework, Engagement Research, Infra Hardening

## Project background (read first — this is the whole context you need)

This document is a research brief for an existing project called `brand-ai-readiness-audit`, built for a
hackathon-style challenge ("Round 3"). Below is everything about the challenge and the project's current state
that matters for this research pass. You do not have and do not need any other file from this project — this
document is self-contained.

### The challenge

The task: build an **Agent Skill Marketplace** — a package of one or more "Agent Skills" (the
agentskills.io format: a `SKILL.md` with YAML frontmatter + instructions, optional bundled `scripts/` and
`references/`), tied together by a marketplace manifest, with exactly one designated **entrypoint skill**. Given
a website URL, the entrypoint audits it and produces a structured **audit report**:

- **Problems found** — issues hurting the brand's *AI discoverability* (why AI assistants don't find/cite it)
  and its *on-site engagement* (why visitors who do arrive don't stay) — each with **evidence** and a
  **severity**.
- **Suggested actions** — prioritized fixes, plus proactive improvements even where no explicit defect was
  found.

It is **recommend-only**: nothing in the marketplace ever modifies a live site, submits a form, or takes a
destructive/authenticated/rate-abusing action. Everything runs read-only, respects `robots.txt`.

Minimum required report shape (a floor, extra fields are fine):

```json
{
  "site": "example.com",
  "audited_at": "2026-09-20T14:32:00Z",
  "summary": { "total_findings": 6, "critical": 1, "high": 2, "medium": 3 },
  "findings": [
    {
      "id": "F-001",
      "title": "No JSON-LD structured data on product pages",
      "severity": "high",
      "evidence": "Crawled 12 product pages; 0/12 contain schema.org markup.",
      "suggested_action": { "summary": "Add Product/Offer JSON-LD to every product page.", "priority": "high" }
    }
  ]
}
```

**Evaluation** is of the marketplace itself (its skills' instructions/checks/logic/composition), not any one
report it produces, on **unseen websites** (no example sites are given — generalization is tested by
construction, so patterns/root-causes matter, not fitting to specific sites). Rubric criteria: detection
accuracy (real problems, evidence-backed, few misses, few false positives), suggested-action quality (correctly
targeted, mechanism-sound, prioritized, non-obvious beyond-problem suggestions), output design (clear structured
actionable report a non-expert could act on), skill-format/engineering hygiene, marketplace composition
(genuine separation of concerns, not padding — a single well-built skill is not penalized for not decomposing),
and generalization.

Guardrails: submission zip ≤ 50 MB (**no pre-trained model weights**), audit runtime < 5 minutes on a standard
machine for a typical website, no browser automation of any kind (see Hard Constraints below).

### Why these signals matter (the underlying mechanism — background, not a checklist)

The challenge is explicitly about encoding *why* a brand is invisible, stale, or gets bounced by AI systems, not
applying a generic SEO checklist. The mechanisms behind that:

- **How search/AI visibility works at all**: a crawler has to be let in, has to be able to read what's on the
  page, and has to be able to pick out the specific fact someone's looking for — in that order. If any one step
  fails, the page is invisible to the machine even though a human sees it fine.
- **How assistants like ChatGPT use sources**: many assistants look things up live — searching, fetching pages,
  building the answer from what those pages say. What becomes a cited source tends to be whatever's easiest to
  reach, read, and quote a clear fact from. If nothing about a brand is easy to reach/read/quote, it doesn't make
  it into the answer.
- **How machines "read" a page**: a page that looks complete to a person isn't always complete to a machine —
  content assembled only after page-load, or held in a non-textual form, can be invisible to a program not
  looking at it the same way a browser does. The more explicitly and unambiguously a fact is stated in plain
  readable text, the more likely it's extracted correctly.
- **Why cross-web agreement matters**: machines trust a fact more when many independent places say the same
  thing; a claim living in only one spot is fragile. A related problem is mistaken identity — several different
  things sharing a name can get merged unless something clearly distinguishes them.
- **Personalization**: assistants can draw on context they already hold about a person (past questions, location,
  stated preferences) and weight answers toward that — part of why two people asking the same question can get
  different brands or framing back.
- **Why machines drop content from summaries**: AI-generated summaries (e.g. of long emails/pages) are built from
  readable text; when the real substance isn't available as text, or the important lines are buried in low-value
  filler, the summary has little to work with and the important part can simply disappear.

The project's existing capability rows below all trace back to one of these mechanisms.

## Hard constraints — non-negotiable, apply to every candidate

1. **No headless/headless-adjacent browsers, ever.** No Playwright, Puppeteer, Selenium, Chromium, `crawl4ai`, no
   rendered DOM, no browser-based JS execution — not even as an optional fallback. Judges run the solution in
   plain Python/Node environments; an optional browser path still fails a browserless grader. Detection must use
   direct HTTP + parsing only: `requests`/`httpx`/Node `fetch`, raw HTML, JSON-LD, embedded JSON, hydration-state
   blobs a page embeds itself (e.g. `__NEXT_DATA__`, `window.__NUXT__`), HTTP headers, XML, static CSS/resource
   inspection, locally computed statistics/heuristics.
2. **Off-site website querying is allowed, but narrowly.** For capabilities involving brand visibility/presence/
   mentions/discoverability/reputation/external corroboration/public discussion, you may directly query public
   sites — Reddit, Quora, forums, review sites, other publicly accessible sources — via direct HTTP GETs,
   robots.txt-respecting. This does **not** reopen general web search or crawling.
3. **No outsourced intelligence.** Never use a third-party API/service that hands back a pre-computed SEO score,
   GEO score, ranking, classification, sentiment score, authority score, visibility score, AI-readiness score, or
   any other proprietary analysis in place of computing it ourselves. If a signal can be computed locally from
   raw retrieved data, it must be computed locally.
4. **No pre-trained model weights**, independent of constraint 5 below — a submission zip must not bundle model
   weights, and a package that *downloads* model weights at install/runtime (a spaCy language model, a
   sentence-embedding checkpoint, any statistical NLP model) is out of bounds even if the package itself would
   otherwise be fine. Rule-based, non-statistical NLP/parsing logic is fine.
5. **Third-party open-source packages ARE now allowed — this is a relaxation from this project's earlier,
   stricter rule.** Earlier in this project, *all* third-party dependencies were banned outright (an automated
   test enforced zero third-party imports project-wide). **That blanket ban is now lifted by the project owner**,
   specifically:

   > Packages that are publicly available and downloadable from the standard Python (PyPI) or Node (npm)
   > ecosystem, and that run **locally** using their own bundled algorithm/logic, are now allowed. What remains
   > categorically banned is consuming a **result** computed by an external party — a hosted API, cloud service,
   > or third-party endpoint that hands back a pre-computed score/ranking/classification/verdict in place of us
   > computing it ourselves. Fetch-raw-and-judge-ourselves: allowed (constraint 2). Download-and-run-an-algorithm
   > locally: now also allowed (this is the change). Outsource-the-verdict: still banned (constraint 3).

   A package that is pure algorithm/data-structure code (e.g. `networkx`, `rapidfuzz`, `python-Levenshtein`,
   `tldextract`, `datasketch`) is fine. A package that ships or downloads model weights is still blocked by
   constraint 4.
6. **Recommend-only, read-only, robots.txt-respecting, audit runtime under 5 minutes, submission zip ≤ 50 MB.**

**Open risk to flag explicitly in every candidate that introduces a new dependency** (name it as a stated risk
in the candidate's own write-up, do not try to resolve it yourself): the grading environment's ability to
`pip install` / `npm install` at build or run time is unconfirmed. A pure-Python/pure-JS package with no
native-binary compilation step and no separate model-weight download is lower risk than one that shells out to a
system binary (e.g. `tesseract-ocr`, which the `pytesseract` package wraps but does not itself install) or that
needs a compiled C extension unavailable in a locked-down sandbox. Score this under "Package footprint" in the
Innovation Filter below.

**This relaxation reopens, for reconsideration only (not automatic re-acceptance), specifically these three
previously-rejected candidates from the prior research pass, whose rejection reason was the old blanket
dependency ban and nothing else** — re-evaluate whether they clear the Innovation Filter now that the blocking
reason is gone, do not resubmit them unchanged:

- **GraphRAG k-core density** (needed `networkx`)
- **Internal PageRank starvation** (needed `networkx`)
- **OpenIE triple-extraction yield** (needed a dependency parser — verify it doesn't secretly need model weights;
  most real dependency parsers do, which would keep this blocked under constraint 4 even though constraint 5
  relaxed)

Every other prior-pass rejection was rejected for a *different* reason (fires on everything, unfalsifiable
threshold, already shipped under another name, conventional-SEO novelty failure, or a specific other reason like
false-positive risk or third-party-service self-containment) — the package relaxation does not reopen those; see
the full table below.

## Area A — Genuinely new capability dimensions

Investigate territory that is genuinely different from everything in the tables above — not another row in an
existing cluster, a re-framing of a shipped capability, or a re-submission of a prior rejection without a new
angle. Under the now-relaxed dependency constraint:

1. **What becomes newly implementable with real packages** that wasn't with stdlib-only code. Graph algorithms
   (`networkx`) applied to something *other* than the two already-flagged-for-reconsideration candidates above —
   e.g., is there a graph-structure signal in the site's own JSON-LD entity graph beyond referential integrity
   (already covered) — some other graph-theoretic property of that same graph? Fuzzy-matching packages
   (`rapidfuzz`, `python-Levenshtein`) applied beyond the uses already named for CIT-11/ENT-06. Rule-based (not
   statistical, not model-weight-based) tokenization/NLP packages.
2. **What AI-specific signals are still missing** — failure modes specific to how modern AI systems actually
   work: retrieval-augmented generation, sparse/dense/hybrid retrieval, reranking, entity resolution, knowledge
   graphs, citation selection, context compression, query rewriting, answer synthesis, agentic browsing, tool
   use, multi-hop retrieval — failure modes an ordinary SEO audit would never detect. Cross-check against every
   table above before proposing; do not repeat a prior-pass candidate under another name.
3. **What unconventional web/HTTP signals remain genuinely unexplored** — HTTP headers, redirects, content
   types, caching behavior, ETags, Last-Modified, canonical chains, alternate representations, link
   relationships, XML structures, feed formats (RSS/Atom), OpenGraph, Twitter/X cards, microformats, hreflang,
   language/content negotiation, static assets, downloadable documents, source-code conventions,
   framework-generated metadata, URL structures, internal linking patterns — that are not already covered above
   and were not already rejected as "fires on everything" or "unfalsifiable threshold."
4. **"Side-channel" signals** — seemingly unrelated website characteristics that indirectly affect the chain
   discovery → retrieval → ranking → context inclusion → citation → answer generation: cache behavior, redirect
   topology, duplicate-content fingerprints, URL entropy, content-version divergence, document update patterns,
   feed/index synchronization, inconsistent entity fingerprints, structured-data contradictions, resource
   availability, response-size anomalies, HTTP-level accessibility patterns.

## Area B — Fresh angles on deferred/blocked items

Most rows tagged "Area B" above were blocked on **"needs multi-page/crawl-wide context, no crawl infra."** This
project already has one working precedent for a *bounded, non-full-crawl* multi-page pattern: a canonicalisation
check reuses a site's own sitemap.xml URL list (already fetched for a separate check) to compare URL variants
across the whole site without ever crawling a link graph — no page-graph traversal, just reading a sitemap that
already exists and sampling from its declared URL list.

For each row tagged "Area B" above, investigate specifically:

- Can the **same sitemap-scoped, bounded-N-page-sample pattern** (not a full crawl, not link-graph traversal)
  unblock it, and at what sample size does it stay inside the 5-minute total runtime budget shared across all 8
  skills?
- If not sitemap-scoped sampling, is there a *different* bounded pattern (e.g. following only same-template
  internal links up to depth 1, capped at N pages) that would work, and what's the false-positive/coverage
  tradeoff versus an actual crawl?
- For **REN-09 (image-of-text facts)** specifically: is there a pure-algorithm (no model-weight) OCR path now
  that packages are allowed? Investigate what real OCR actually requires — the most common real OCR path
  (Tesseract, wrapped by the `pytesseract` package) needs a system binary that the Python package itself does not
  install, which may not clear the "downloadable from pip/npm, run locally" bar the same way a pure-Python
  package does. Flag this distinction explicitly rather than assuming OCR is now unblocked by the relaxation.
- For **CIT-11 (hearsay provenance)**: does a fuzzy-matching package make the claim-vs-forum-opinion text
  matching tractable at an acceptable false-positive rate, or is the underlying blocker semantic (not lexical)
  and therefore unaffected by better string matching?
- For **cross-page near-duplicate/template dilution**: the rejection reason was a sampling-bias problem in this
  project's own agent-chosen page sample (it tends to pick "interesting-looking" pages, which hides exactly the
  near-duplicate clusters this check would look for), not a technique problem. Is there a sampling strategy
  (stratified by page template rather than by apparent interest) that would fix the methodology rather than the
  detector?

## Area C — On-site engagement research

The engagement cluster (EN) is explicitly authored by the project team, not derived from the same kind of

## Area D — Infrastructure hardening

These are not audit checks the report surfaces to the user — they are the machinery the 89 audit rows run on
top of. Investigate, now with real packages available:

- **Page sampling plan**: what does stratified/representative sampling literature (survey sampling,
  software-testing test-selection literature) say about picking a small, diverse page set from a sitemap without
  a full crawl, in a way that maximizes template/content-type coverage for a fixed page budget? This directly
  feeds Area B's "bounded sampling" question too — treat them as the same underlying research question seen from
  two angles.
- **Fetch layer / page bundle**: caching-systems and single-fetch-many-consumers patterns (one fetch of a page
  feeding every skill that needs it, instead of each skill fetching independently) — what's the simplest correct
  implementation given a real HTTP client package is now allowed (e.g. a connection-pooling/HTTP2-capable client
  vs. the stdlib HTTP client)?
- **Deduplication/aggregation of findings**: this project checked twice already for cross-skill redundant
  findings across 4 real composed reports and found no real case yet. Is that because it's genuinely rare, or
  because the 4 test sites weren't the right test? What near-duplicate-text-detection technique (e.g. MinHash/
  LSH via a package, or something simpler) would be the right tool *if* a real case appears — note that a
  SimHash-based near-duplicate technique was rejected above as an audit *capability* aimed at the target site's
  own content (methodologically broken against this project's page-sampling bias), but that says nothing about
  whether the same underlying algorithm is useful applied to a completely different problem: deduplicating this
  project's *own findings output* across its 8 skills, not the target site's content.
- **Budget/timeout governor**: given the hard <5-minute total-runtime ceiling across all 8 skills, and a now-
  larger dependency surface (real packages carry real import/initialization cost), what's a defensible per-stage
  time-budget allocation, and what degrade-to-`unknown` policy avoids a partial audit silently under-reporting
  instead of honestly flagging incompleteness?

## Innovation Filter

For every proposed capability or infrastructure improvement, score it on:

1. **Novelty** — Would a typical SEO/GEO auditor already do this? Does it duplicate anything in the Implemented,
   Rejected, or Deferred tables above?
2. **AI relevance** — Does it specifically affect retrieval, grounding, citation, synthesis, or agent usability
   (Areas A/B), or does it genuinely improve report quality/coverage/runtime (Areas C/D)?
3. **Implementability** — Can it be implemented in Python/Node, browser-free, under the relaxed dependency rule
   (hard constraints 1–6 above)?
4. **Evidence quality** — Can the detector produce concrete evidence rather than an opinion?
5. **False-positive safety.**
6. **Computational cost** — inside the 5-minute total-runtime budget, shared across all skills.
7. **Package footprint** — name the exact package(s), PyPI/npm, license, pure-language vs. native-binary/
   compiled, approximate install size, and whether it requires any network access or model-weight download at
   install or run time. Flag any native-binary or model-weight dependency as elevated risk.
8. **Differentiation / judge "wow factor"** (Areas A/B) or **report-quality/robustness impact** (Areas C/D).

Strongly prioritize ideas that are: **simple to implement + technically defensible + unusual or genuinely
missing + produce surprising or high-confidence findings + low package risk.**
